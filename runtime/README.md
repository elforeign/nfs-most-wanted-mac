# port/runtime: the native runtime

`boot.c` loads the user's `speed.exe` into guest memory at its own addresses and builds a TEB (`fs:`), a 1 MB stack and a bump heap. It points every IAT slot at a synthetic thunk, then calls the translated entry point (`007C4040`) from `../recomp/out/speed.a`. `imports.c` (generated) maps IAT slots to `DLL!function`.

```sh
python3 ../recomp/build_all.py   # with tools/.venv/bin/python: translate + compile the game
./build.sh                       # link boot
BOOT_TRACE=1 BOOT_TIMEOUT=10 ./boot "/path/to/Need For Speed Most Wanted Black Edition"
```

                
                                                                                       
                                                               
                                                                                                                                                                                                                                                                                                                                                                                                                                                            
                                                                         
                 

Win32 subset: version, heap (`heap.c`: size-class slabs plus page runs, bookkeeping host-side; process heap at 0x10000000-0x30000000, resource heap for `gmalloc` at 0x50000000-0x7F000000; standalone test: `cc -O2 -DHEAP_TEST runtime/heap_test.c runtime/heap.c`) and virtual memory, TLS, critical sections, startup info, std handles, command line, environment, code pages and string mapping (Latin-1), locale stubs, time/performance counters, interlocked ops, events, mutexes and semaphores, threads (pthreads under a guest lock, `threads.c`), the game's registry key (below), files (paths resolved case-insensitively under the game folder; `USERDATA` is `~/Library/Application Support/NFSMW-port`), `cpuid` (a generic Pentium 4 class CPU; `rdtsc` ticks at 3 GHz). D3D9 + D3DX effects on Metal (`d3d9.m`, `render.m`, `d3dx_effect.c`), DirectSound on the host mixer (`dsound.c`), DirectInput keyboard/mouse, USER32 on Cocoa (`user32.m`), X360 movies (`movies.c`).

The game boots, plays the intro movies, runs the front end and races (2026-10-19: one frame per sim tick at the display's refresh rate, 120 fps on ProMotion, at performance level 4 with diagnostics on; ~3 ms of CPU per frame; see Frame rate and timing).

Examples using `TOOLS_PY` or `NFS_RUNS` assume `runtime/env.sh` has been sourced from a runtime script; from the checkout root, set `TOOLS_PY="$(pwd)/../tools/.venv/bin/python"` and `NFS_RUNS="$(pwd)/../.runs"` (or use your configured paths).

## The app (`app.m`, `bundle.sh`)

`runtime/bundle.sh` (after `build.sh`) makes `runtime/NFSMW.app`: `boot` as the executable, an Info.plist (racing-games category, Game Mode, high resolution, game controllers), a generic speedometer icon drawn by `app_icon.m`, and an ad-hoc signature. Double-click it, or `open runtime/NFSMW.app` (`--env BOOT_USERDATA=<scratch>` for test runs; `--args <game folder>` sets the folder without the panel). As an app:

- **Game folder:** asked for with an open panel on the first launch (hold Option at launch, or NFSMW > Change Game Folder…, to choose again) and kept in `USERDATA/app.txt`. A folder is accepted only when its `speed.exe` has the PC v1.3 code the game was translated from: a code fingerprint over the .text/.rdata/.data bytes and PE layout (headers, timestamp, resources and appended data are ignored; a repack with the same code is accepted; `recomp/exe_fingerprint.py`), which `build_all.py` writes into `recomp/out/table.c`; a different region is named in the message. `runtime/boot <folder>` checks the same. X360 extras come from the X360 root Setup records in `roots.txt`.
- **Window:** starts full screen: a borderless window over the whole screen (below the camera housing on notched MacBooks) with the Dock and menu bar hidden, no Space of its own, so Cmd-Tab is instant. The green button, Window > Zoom, or View > Enter Full Screen (Ctrl-Cmd-F) switch between that and a normal resizable window (one point per pixel / backing scale, shrunk to fit the screen); the choice is remembered in `app.txt`. The back buffer is scaled to fit either way (black bars, mouse mapped back through the fit), so the game's resolution and the window size are independent. The widescreen "native" mode is the full-screen size below the camera housing (3456x2160 on a 16"). The system cursor is hidden over the game only (it draws its own). `runtime/boot` follows the game's own choice (its captionless window is full screen); `NFS_FULLSCREEN=0|1` overrides both.
- **Quit:** Cmd-Q, the red button and the Dock all send WM_CLOSE, so the game leaves through its own exit path (`ExitTheGameFlag`, `DeInitializeEverything`, `ExitProcess`); a second Quit while it shuts down quits at once.
- **Focus:** when the window loses focus, held keys and buttons are released and the gamepad reads neutral, and the game is told (WM_ACTIVATEAPP), so it pauses itself as on Windows (it waits in `GetMessageA`, with the guest lock released). `runtime/boot` from a terminal keeps running in the background so scripted runs work; `NFS_PAUSE_INACTIVE=0|1` overrides either.
- **Logs:** `~/Library/Logs/NFSMW-port/NFSMW.log` (the previous run in `NFSMW.previous.log`; Help > Show Logs in Finder). Each running copy has its own log: a copy started while another runs writes `NFSMW-2.log` (a lock file, `NFSMW.lock`, marks the one in use), so it never moves a log that's still being written. Crash reports without `BOOT_DIAG` go to the same folder (`NFSMW-crash.txt`, `NFSMW-2-crash.txt`); a fatal runtime error on the main thread also shows an alert. `BOOT_LOG=<file>` writes elsewhere, `BOOT_LOG=-` keeps stdout. `runtime/boot` keeps printing to the terminal.
- **Defaults:** no diagnostics, and audio output chosen for the device (Audio mode below).
- **Performance overlay** (`overlay.m`): View > Performance Overlay > Off / Compact / Full, Cmd-Option-P cycles; saved as `overlay` in `app.txt` (default off); `NFS_OVERLAY=off|compact|full` overrides. Compact: fps, frame ms p50/p99, sim rate. Full: 4 s graph (frame interval, game-thread CPU, GPU, frame budget), the game thread's busy/sleep/GIL/GPU-wait split, sim ticks per frame with catch-up and repeated frames, GPU ms, draws, background shader compiles, texture uploads, memory (RSS, guest heaps, GPU textures/buffers, HD vinyls/skins), back buffer / window size, aspect, post chain, shadows, antialiasing, audio output and device, controller and rumble motor levels. Its own sublayer at the window's backing scale, filled by the presenter queue; the counters are the always-on per-frame ring stats.log also uses (`perf_frames` in `diag.c`), so its numbers match stats.log. Works in `runtime/boot` too. Cost (solo A/B 2026-10-20, 15.1.1, 3 interleaved pairs, native res + 4x MSAA + shadows 2 + X360 chain): `full` vs `off` +0.02 busy ms, +0.05 GPU ms per frame, p99 9.43 vs 9.44 ms, inside the ~0.5 ms run-to-run scatter: no measurable cost.

Closing resumes from the same tick, at the normal rate (checked: `frames.log` simtime 14.9832 for the 1000 frames the menu was open, then +1 tick per frame; the HUD race clock reads 5.30 in every capture while open). In the front end nothing is frozen (input only). The game's own window procedure (FUN_006db6c0) doesn't handle F10 (it handles End, Home, Left, Right, F12 and Ctrl), so the menu takes F10 from it; F10 can't be bound in Options > Controls while the port runs.
- **What it holds:** the switches that make sense to users, live where the code allows: window mode, performance overlay, post-processing, tone curve, car glass, raindrops, mirror brightness/detail, audio output, button layout and rumble. Road reflection, mirror resolution/anti-aliasing and shadow fit apply through the game's device reset at the next frame. World streaming is live when launched with Ahead; car paint and rain ripples are live when launched with X360. The remaining settings carry a ⟳ (restart via Display & performance > Restart game); see the lifetime audit below. A switch set in the environment wins: the row shows "set by NFS_X=..." and can't be changed.
- **Saved** in `USERDATA/app.txt` (the same file as the window mode and the Audio/Controller/View menus; those keep their keys, so both stay in step), only when changed. At start-up a saved value that differs from its default is exported to its `NFS_*` switch (unless the environment set it), so the code that reads its switch once keeps working unchanged.
- **Adding a setting** (from your own file): a static `Setting` with id, category, label, help, type (`SET_TOGGLE`, `SET_CHOICE`, `SET_SLIDER`, `SET_TEXT`, `SET_ACTION`, `SET_INFO`, `SET_HEADING`), choices and their switch values, default, `env`, `restart` or an `apply(value)` for live changes, registered with `settings_add()` from a constructor; read it with `settings_get(id)`. The header (`settings.h`) has a worked example.
- **Drawing:** a Core Animation layer over the game's at the window's backing scale (sharp at any game resolution), its bitmap drawn with CoreText at most once a frame and only when something changed (once a second for the live readouts; ~10-15 ms at 2x on the game thread, only while open), plus a dim layer; nothing is drawn while closed. With `BOOT_DIAG_SHOTS` and the menu open, `menu_NNNNN.png` is the panel with alpha (the frame PNG has the game without it). `BOOT_DIAG` logs `menu:` lines (open/close, tab, every change, the panel's size and time).
- **Tests:** `BOOT_KEYS` keys `F10`, `TAB`, `Q`, `E`, arrows, `RETURN`, `BACK`, letters typed into a text field; steps `race:N` (N ticks after the race state began), `pad:0x2000` (touchpad click, with `BOOT_PAD=sim:`; bit 12 is PS/Guide) and `pad:MASK:N` (held N ticks, e.g. `pad:0x300:40` for L3+R3).

**Diagnostics** in the menu: the performance overlay modes, a live readout (fps, p99 frame time, GPU time over the last second; the audio output and device), **Report a problem** (what's wrong: Audio / Graphics / Controls / Gameplay / Crash-freeze / Other; an optional note typed on the keyboard; Save report), Show reports / logs in Finder, and **Full diagnostic logging** (from the next launch: `BOOT_DIAG=<userdata>/logs/<YYYYMMDD-HHMMSS>`; turn it off afterwards).

### Live changes and Restart game

**F10 > Display & performance > Restart game** confirms inside the menu (works with a pad): the first press shows "Press again within 4 s to restart; race progress since the last save is lost.", a second press within 4 s restarts. (Was a modal NSAlert until 2026-10-23: a pad could not answer it, and the frozen frame loop behind it tripped the 15 s hang watchdog.) **Quit game** (row above it, 2026-10-26) closes the game the same way (two presses within 4 s, settings saved, then the Mac's Quit path), so a pad player never needs the keyboard.
Cancel is the default button. On confirmation, `app.m:138` writes, flushes and fsyncs the current settings to a
staging file and atomically renames it to `app.txt`; a save error cancels the restart. Quit then follows the existing
NSApp delegate -> `user32_request_close` (`user32.m:502`, rumble/lightbar off, WM_CLOSE) -> game shutdown ->
`ExitProcess(0)` (`boot.c:788`) path. The existing guest CloseHandle path fsyncs and atomically installs completed
saves (`boot.c:510`); the host audio exit handler closes both live and parked outputs (`host/audio/dsound_host.cpp:757`).
This does not save unsaved race progress. Fatal exit, TerminateProcess and forced Quit do not arm a replacement.

The restart handler is registered before the other runtime exit handlers (`app.m:93`), so their cleanup runs first.
It spawns the same executable as a small waiter; `EVFILT_PROC/NOTE_EXIT` waits for the old process to exit before
`execve` starts the replacement (`app.m:48`, `app.m:70`). There is no overlapping game instance. The launch arguments,
working directory and original launch environment are preserved. The snapshot precedes `settings_init` and
`report_init`: internally exported **old saved settings** and generated diagnostic paths must not override the
new `app.txt`. Explicit environment overrides remain overrides. Direct execution of a bundle's own
`Contents/MacOS/NFSMW` keeps that same bundle; terminal launches re-execute `runtime/boot`.

With **either `BOOT_DEADLINE` or `BOOT_BACKGROUND` present**, the item reports "Restart disabled in unattended
runs" and does not show a modal, quit, or spawn. Both preparation and the exit handler also check this restriction.
The waiter repeats the guard check. Spawn/exec failures are reported on stderr; it never launches a fallback copy.

The complete audit of the **11 formerly unconditional restart rows plus the two audio rows** is **7 live
(including conditional world streaming), 0 next-load, 6 restart only**. No default or shader/audio math changed.
"Restart only" means the current port retains boot-loaded guest resources; replacing them safely would require a
larger reload path. No race/front-end load was found that reconstructs the entire affected resource set.

Car paint and rain ripples already have conditional restart semantics (`live_from_default`), rather than the 11
unconditional rows above: `materials.m:306` / `materials.m:353` update uniforms in shaders translated at startup.
Their help now also names Restart game for a run started with PC shaders. World streaming uses that existing

exceed the contained-change limit and/or require replacing guest data layouts.

The four render-resource changes only queue the game's existing `LoadedFlagMaybe` reset byte (`x360.m:53`).
At the beginning of `eDisplayFrame`, before drawing, the game releases old targets, resets the device and recreates
the targets (per the decompilation). This is the resolution-change path already used by
`widescreen.c:101`. Setters never recreate textures or pipelines inside an encoder. Pending target values are
consumed at recreation, so old dimensions, samples, border and culling stay consistent until then. Several changes
in one message-pump pass coalesce into the same reset. This is a full device reset; it can cause a short frame hitch.

**Problem reports** (`report.m`): `<userdata>/reports/<YYYYMMDD-HHMMSS>/` (a `-2` suffix for two in one second; the saved path shows in the menu):
- `report.txt`: the summary first: when, category, note, reason (the F10 menu, or the crash / hang), build id (commit, `+` if built with local changes, build time) and the speed.exe hash, game state (game-flow, frame, seconds since start), display (screen, pixels, Hz, backing scale), render (back buffer, MSAA, post chain, shadows, car paint), audio (output format, device, underruns), controller and layout, the last minute in numbers (fps mean/min, worst p99, GPU mean), the settings that differ from their defaults or are set by a switch, and the file list;
- `screenshot.png`: the game frame when the menu opened (full size, without the menu);
- `stats.txt`: one line a second for the last 3 minutes: time since start, frame, fps, p50/p99/max frame ms, game-thread busy ms, GPU ms, game-flow state, mix RMS per channel;
- `events.txt`: the notable events of the run (game-flow changes, frames over 500 ms, audio output and default-device changes, underruns, setting changes, menu use, reports, hangs, crashes), then the last 400 lines of the diagnostic event ring;
- `log.txt`: the last 256 KB of this run's log (stderr, when it goes to a file: `NFSMW.log` in the app);
- `settings.txt`: every setting, its value and source (`default`, `app.txt`, `env NFS_X=value`);
- `crash.txt`: crash and hang reports only: the diagnostic report (every thread's backtrace, guest stacks, events).
The stats and events rings are always on, in normal play too (a few stores a frame, one small computation a second), so a report has the last minutes without `BOOT_DIAG`. A crash (`crash.txt` from the signal handler or a fatal runtime error) or a hang (diag mode's `hang_N.txt`; without `BOOT_DIAG` a watchdog reports no frame for 15 s while the game isn't idle on purpose) writes a report folder by itself, category Crash-freeze (at most 3 a run).

**Session log** (`report.m`, always on, no `BOOT_DIAG`): every run writes `~/Library/Logs/NFSMW-port/sessions/<YYYYMMDD-HHMMSS>/` (under `BOOT_USERDATA` when that is set, so launcher runs land in the scratch profile; the newest 20 are kept), so a session can be inspected without a test launch:
- `session.txt`: the setup (build, macOS, Mac model and chip, display pixels / Hz / scale, back buffer, MSAA, post, shadows, power source, thermal state, settings that differ from their defaults), then every `report_note` as it happens (game-flow, settings, display / power / thermal changes, audio output, device and underruns, menu use, stalls), a `HITCH` line per frame over budget, and a `SUMMARY` per game-flow state every 20 s, then every 60 s, and at a normal exit (a crash or hang writes one too; a SIGTERM does not, so the last periodic one stands).
- `perf.tsv`: a line a second (header first): fps, frame ms p50/p99/max, busy ms p50/p99 (game thread minus waits), mean idle ms (sleep, GIL, drawable wait, GPU wait), GPU ms mean/p99, draws and sim ticks per frame, frames over budget, RSS MB, player car x/y/z and speed (0 outside a race), whether the F10 menu is open, the presentation counters, then the device mix of that second: RMS per channel `rms_fl rms_fr rms_c rms_lfe rms_sl rms_sr` and peak per channel `peak_*` in dBFS (-120 = silent; empty while a movie plays, which reads the mixer itself), and `clip`: samples (all channels) at or over full scale (>= 32767/32768) before the mixer's clamp, then `dip_fl .. dip_sr`: per channel the RMS of the quietest 50 ms stretch of the second in dBFS (a cutout shorter than a second shows here, not in `rms_*`). Each stats reader (this pass, BOOT_DIAG's `mixrms`) folds the mixer's one window into its own accumulator (`dsound_mix_levels`, `runtime/dsound.c`), so both see the whole second. From build 1592 the last columns are `thermal` (0 nominal .. 3 critical, -1 unknown), `low_power`, `app_active`, `occluded`, `fullscreen` and `gpu_wall` (mean ms from the command buffer reaching the GPU queue to its end, against `gpu_mean` = GPU start to end); `session_report.py` lists "GPU slow while draws unchanged" stretches (gpu_mean > 2x the median at +-25% draws) with them.
- A hitch is a frame over the budget (1.5x the interval: the display's, or the sim rate when lower) and over 1.5x the previous second's median (so a GPU-bound run is not all hitches; the over-budget share still counts every such frame), after frame 600 and not while the game idles on purpose. Each `HITCH` line: frame ms, busy, idle split, GPU ms (the frame's, found by serial, the largest of three neighbours: approximate), ticks, state, the causes of this frame or the one before (`compile`: shaders / pipelines made or draws deferred, `flow`: game-flow change, `menu`, `audio`, `catchup`: more than one sim tick, else `unknown`), the shader / pipeline / deferred deltas and the car position. At most 5 lines a second, then a count; the SUMMARY counts each hitch under its first cause. Streaming / section loads are not attributed: the TrackStreamer has no counter that is cheap without `BOOT_DIAG`.
- Cost: per frame a few loads and counter increments (`report_frame`: state histograms, the render counters, one ring copy for a hitch); every write is in the once-a-second pass or a note, never per frame.
- GPU-client telemetry (`gpuclients.m`): appends `gpu_dev_util`, `gpu_self_ms`, `gpu_other_ms`, `gpu_top`, `gpu_mhz` after `gpu_wall`, preserving every earlier column. A utility-priority background sampler reads AGX via IOKit once a second; the frame path only copies a cached result without waiting. `gpu_dev_util` is Device Utilization %. Client times are deltas of summed AppUsage accumulatedGPUTime (ns), normalized to ms/s using the measured interval; self is this PID, other is every other PID. Baselines use registry entry IDs, so newly seen clients, PID changes and counter resets contribute no lifetime totals. `gpu_top` holds the top three other process names and ms/s (`name:ms,name:ms`, grouped by name); TSV/grammar separators in names become `_`. Missing counters, the first sample, and caches older than 3 s produce `-`.
  `gpu_mhz` uses optional dlopen/dlsym IOReport GPU Stats / GPU Performance States residency deltas: the residency-weighted mean of explicitly labelled MHz/GHz states, excluding idle/off states. Opaque names produce the dominant active `state=NAME` instead; missing library/symbols/subscription/data produce `-`.

## Frame rate and timing (`pacing.c`)

Session setup and display-change notes include the screen's current, potential and reference EDR headroom (sampled every 5 s). These are AppKit colour-component limits, not an HDMI HDR signal-mode flag; `HDR transport=unknown` is explicit because the public CoreGraphics display API exposes no such getter. The port continues to output SDR sRGB even when the screen has EDR headroom.

The game simulates in fixed ticks (`Scheduler::Run`, 00642E60; 1/60 s in the original) and renders once per main-loop pass. Its own limiter alternates ~16/~4 ms frames on a fast CPU, and the short ones run no tick, so they repeat the previous picture (pixel-identical in `BOOT_DIAG_SEQ` captures). With `NFS_FRAMEPACE=sim` (default):

`NFS_FRAMEPACE=game` restores the original: 60 Hz ticks, the game's limiter (~95-100 fps counted, ~40 % repeated frames) and its real-time counter. `BOOT_KEYS seq:` scripts count `wait:`/`idle:` in 1/60 s of real time, so they behave the same at any frame rate.
- **Loading waits poll every 1 ms, not 8-10** (`NFS_SLEEP_IOWAKE`, default on, 2026-10-25                                                         ): the game's loading waits poll with `THREAD_yield(8)` (alertable `SleepEx`), one loading step per poll, so `TrackStreamer::WaitForCurrentLoadingToComplete` (00730390; from `BlockUntilLoadingComplete` 007317A0, `MakeSpaceInPool` 00730BF0: a NIS or HUD load after a career event warp) froze one frame for 17 polls x 10 ms (the session's 169 ms 'sleep' frames). ## CPU cost of a frame

Race 11.1.1 at level 4, 1280x720, diagnostics on: the game thread is busy ~3 ms per frame (`stats.log` `busy`), down from ~13 ms. What changed (git log `8f5ceab`, `c022d63`): Present no longer waits for the GPU (one frame in flight, resources rewritten by the game while a pending frame reads them are renamed); draws build no Metal descriptors and skip bindings the encoder already has; float constants upload only the registers a shader reads, only when changed; `CommitChanges` applies only what changed (D3DX semantics); the game's 100 Hz TIMER thread no longer spins (absolute waitable-timer times); guest threads only take the GIL when their wait is satisfied; the recompiled code keeps registers in host registers across guest memory accesses (`recomp/README.md`).

`NFS_RENDER_THREAD=1` (`render_thread.m`                                                              ): Metal encoding leaves the game thread. Command buffers become recorders (encoder calls appended as compact ops, `set*Bytes` copied, objects retained once per buffer); one render thread replays them in commit order into real command buffers and commits; the present queue's drawable work waits for the frame's real commit. Translation, uploads and object creation stay on the game thread; the bound is the existing one-frame-in-flight wait. With `BOOT_DIAG` the `render thread:` event gives buffers per second, recorder commit -> real commit (mean/max) and replay ms. Default `1` since 2026-10-26 (solo A/B a,b,b,a at race 1.2.1 4K AA 2x, 3,550 draws: game thread busy p50 7.36 -> 6.21 ms, p99 8.39 -> 7.27; replay adds 0.81 ms between the game's commit and the GPU commit); `0` = the direct encoder calls.

`dinput.c` exposes the first GameController.framework extended gamepad (DualSense, DualShock, Xbox, ...) as a DirectInput gamepad laid out like the 2005-era "Controller (XBOX 360 For Windows)": X/Y left stick, Rx/Ry right stick, **six axes from the first enumeration: LT on Z and RT on Rz, independently**, 12 buttons, D-pad as POV. Triggers encode release/half/full as 32768/49151/65535 in the default 0..65535 range (custom DirectInput ranges are preserved); release is the centre of a positive half-axis. **Connect a controller at any time** (asleep at launch, plugged in or reconnecting later, swapped for another): the game enumerates its devices once at start-up (FUN_006dc540), so its gamepad is always there from start-up, read centred and named after the Xbox 360 pad until a controller connects; the first one to connect then takes it over live (its name, layout, binding set, glyphs and rumble), and pad prompts switch to it. A controller that goes away reads centred, nothing pressed (DIERR_INPUTLOST would have left the game holding the last state: `FUN_007f28a4` keeps it on an error). The app log says `boot: controller connected: ...` / `boot: controller disconnected ...` / `boot: no controller connected yet ...`. Start-up still waits up to 0.5 s for GameController discovery, so a pad already on names the gamepad from the start. The game's PC defaults for it (Options > Controls, controller page, all remappable): Accelerate Button 1, Handbrake 2, Brake 3, Speedbreaker 4, Look Behind 5, Reset 6, N2O 7, Pause 8, shifting/camera unbound, D-pad for Engage Event / Blacklist / World Map / SMS.

**PlayStation pads, native** (`padbind.c`, `dinput.c`                                                              ): a DualSense, DualShock 4 or DualSense Edge is detected automatically and given to the game as itself: the Controls screen's joystick page is titled "Controller (DualSense)" ("Controller (DualShock 4)", "Controller (DualSense Edge)"; any other pad shows its own name, e.g. "Controller (Xbox Wireless Controller)") and every control is bindable in the game's own remap UI under PlayStation names: Cross Circle Square Triangle, L1 R1, L2 R2 (analog: each is one axis half), L3 R3, Create (Share), Options, PS, Touchpad, the D-pad, both sticks per direction (Left Stick Up, Right Stick Down, ...), the Edge's paddles. No hard-coded mapping: the game's binding table drives the car and the menus. Defaults = the PS2 layout below (the Xbox 360 defaults translated through what the PlayStation layout did, plus right stick gas/brake, R3 speedbreaker, R2/L2 shift, which now need no binding); menus keep ✕ accept, △ back, ○ □ Create Options for the console prompts; the PS button and the touchpad click are bound to nothing; they reach the game (bindable) unless one is the F10 menu's shortcut (F10 > Controls "Controller: open this menu": by default the touchpad click). Reset to defaults on the page gives them back. The PS button belongs to the game while it is frontmost (no Launchpad). The Controls screen's own keys work from the pad: Circle = Defaults (key 1), Square = Clear (key 2), Triangle = Done. Each controller type (the pad's name) has its own binding set per profile: the game's profile keeps the active one, `USERDATA/pad_bindings.txt` all of them (written at each profile save and type change), so a profile loaded with another pad, or a pad of another type connected while playing, brings that type's own set (or its defaults) back; a profile saved before this counts as the Xbox pads' set. Glyphs: PlayStation art with a PlayStation pad whatever the Controller menu says; the controller-diagram loading screen's labels follow the bindings. The Controller menu's layouts below apply to Xbox and other pads only. `BOOT_DIAG`: `bindings.txt` (the table at each defaults / profile load / save / type change / bind capture), `padbind:` lines in events.log (the Controls actions' values as they change, captures, type changes), `pad: identity` lines.

The Controller menu (PlayStation Layout / Xbox Layout, saved as `pad_layout` in `USERDATA/app.txt`, applied at once) or `NFS_PAD_LAYOUT`, which overrides it, picks how the physical buttons reach those while driving (`user32.m` `pad_apply_layout`), so that the PC defaults give each console version's layout from its manual:
- `playstation` (default, PS2 manual): ✕ or right stick up gas, □ or right stick down brake/reverse, △ look back, ○ or R3 speedbreaker, R1 e-brake, L1 nitrous, R2/L2 shift up/down, Create reset car, Options pause.
- `xbox` (Xbox manual): right/left trigger gas/brake, A e-brake, B nitrous, X speedbreaker, Y look back, RB (the Black button) change camera, right stick up/down shift, Back reset car, Start pause.

For non-PS pads, Xbox layout now defaults Accelerate to Rz+ `(7,0,2)` and Brake to Z+ `(5,0,2)`, retaining each physical pressure (half travel = half demand, including both pedals together). PS2 layout keeps Button 1/3 face/right-stick gas/brake, removes the obsolete combined-Z pedal halves, and defaults trigger shifts to Z+/Rz+. Trigger shift button aliases are suppressed during remapping so capture records the axis. Xbox right-stick shifts still send Buttons 9/10, and camera Button 11; these remain available to bind: bind them once in Options > Controls (press the layout's shift/camera control in the binding field). In menus and the pause menu the buttons are the console version's, matching the console prompts: PlayStation ✕ accepts, △ goes back, ○ / □ / Create / Options do what the CIRCLE / SQUARE / SELECT / START prompts say (the PC keys 1 / 2 / 3 / 4); Xbox A, B, Y, X, Back, Start the same way; L1/R1 (LB/RB) the tab arrows. The PC's own front-end mapping had Button 2 accept, Button 3 go back, Button 1 do key 1 and no pad button for keys 2-4 (so on a real Xbox 360 pad B accepted); keys 2-4 now go in as DirectInput key presses from the pad (`user32.m` `pad_apply_layout`). Menus are told from driving by the FE package in control (the race results come up while the sim runs). **Re-mapping in Options > Controls:** while the game waits for the input to bind (the input object at `IOModule` 0x920DE0 +8: +0x183C, device +0x1840 = 3; set by `FUN_00628C00` when a field is picked, cleared by `FUN_00634900` when it captures), the controller sends the driving mapping, so a binding records what the button does while driving (✕ = Button 1, the Accelerate default), the right stick is only its axis (Y Rotation), and a button held when the wait starts (the ✕ that picked the field) or ends is ignored until released. Before this (2026-10-20, padprompts until padgas) a field bound with ✕ got Button 2 (✕'s menu Accept) and the game cleared the action that had Button 2 (Handbrake); ○ gave Button 1 (key 1 in menus). The user's profile ended with Accelerate = Button 2 and Handbrake = Button 1, so ✕ and right stick up (both Button 1 while driving) pulled the handbrake. Such a profile needs its controller fields re-bound (Accelerate ✕, Handbrake R1, ...) or the controller defaults restored.

Binding persistence is now v2: `USERDATA/pad_bindings.txt` starts with `# NFSMW pad bindings v2`, and each key includes `native_ps`, `nonps_ps2` or `nonps_xbox` along with profile/name hash. Changing a non-PS layout saves the old variant and loads the selected variant even with the same pad name. Only legacy non-PS records are migrated on first use: old combined-Z gas becomes Rz+ in Xbox mode (brake stays Z+); PS2 mode removes those pedal halves. Exact original default action pairs get the new defaults; other custom button choices survive. Old rows remain under `legacy`, and the original sidecar is retained byte-for-byte as `pad_bindings.txt.v1` before the first migration write. Native PS values/name hashes are never converted; a no-op load or swap does not rewrite the sidecar. Profile-only legacy sets follow the same path; a known v2 set is never reclassified as legacy when loaded with another pad. Normal profile saves/type or layout swaps persist changed binding sets.

**Rumble:** the X360 version's model (`feedback.c`), with the game's "Rumble" option (Options > Controls). LocalPlayer::DoFFB feeds the player's IFeedback every sim tick (per wheel: slip, skid, speed with the road surface; shift kicks, nitrous, engine damage, gear changes) and OnCollision on contacts; on PC those methods were empty stubs and any DirectInput pad took the steering-wheel branch instead, so the hook on DoFFB (006EE490) runs it without the wheel, as on the console. Oscillators from the surface's rumble curves (the same data as the X360's ATTRIBUTES.BIN) and event envelopes make a heavy (left) and a light (right) motor level, 0..1, combined and scaled exactly as the X360 sends them to XInput. Every tyre reads the surface under it (`BOOT_DIAG` writes all 47 surfaces' curves to `surfaces.txt`): asphalt, cobble, concrete, wet road, metal and the like only have the wheelspin (slip) curve, so they rumble on burnouts; grass, grass shoulder, dirt, gravel, sand, mud, snow, hay and golf add a speed hum (from 5 m/s, with 1 and 4 Hz pulses); wood/organic pulse instead; a blown tyre counts as dirt; no surface has a skid curve. All on the heavy motor; the light motor comes from events. Opening F10, pausing the game, losing window focus or deactivating the app posts zero to both motors immediately and suppresses further rumble until every hold clears (the game's Sim pause state is checked each main-loop pass, pad read and feedback resume). Closing/resuming discards the old oscillators and event envelopes; only the game's next feedback update can rumble again. The HID queue also gates pending reports, so pad reads or reconnects while held cannot restore old levels. The motors also stop when the game quits (Quit, exit, SIGTERM/SIGINT), and reports go out on their own queue, never blocking the game thread. Collisions use the X360 strength: how much the contact changed the car's velocity (scrapes are light, crashes full), with the port envelope changes below. The pad reports no DirectInput force feedback. `rumble.m` plays the levels on a DualSense (USB or Bluetooth) through its compatible-vibration mode, an HID output report (CoreHaptics through GameController.framework refuses unsigned processes). Other controllers don't rumble yet. `NFS_RUMBLE=off` leaves the controller alone (scripted or unattended runs; the model and its diag lines still run). With `BOOT_DIAG`, `feedback:` lines give each suppress/resume transition (reason, remaining hold mask, motors zero), each second's calls, the per-wheel inputs and each source's motor level. Offline regressions: `feedback_test.c` checks immediate stop, continued game updates while held, overlapping menu/pause/focus/app holds and fresh feedback after resume (29 checks; pre-fix model with missing hooks: 19 failures); `rumble_test.m` intercepts HID writes to check USB/Bluetooth queue suppression, resume and `NFS_RUMBLE=off` without opening a controller (15 checks). Compile/run commands are in their headers; both pass under AddressSanitizer/UndefinedBehaviorSanitizer.

## Focus loss and hidden windows

The window's key/resign-key changes reach the game as WM_ACTIVATEAPP / WM_ACTIVATE / WM_SETFOCUS / WM_KILLFOCUS, as on Windows (in NFSMW.app; `runtime/boot` from a terminal doesn't pass a real focus loss on, so background scripted runs keep going, but `unfocus:`/`hide:` steps do; `NFS_PAUSE_INACTIVE=0|1` overrides). Inactive, the game mutes its sound (`SetSoundControlState(..., "LostFocus")`) and parks its main loop in `GetMessageA` until a message arrives, so it pauses (a race clock doesn't advance); `GetMessageA` waits with the GIL released, so the sound and streaming threads keep running, and diag mode doesn't count the wait as a hang. Keys held at the moment of focus loss are released (their key-ups go to the other app). Presenting never blocks the game: the frame is copied and a presenter queue takes the drawable, so a covered or hidden window (whose layer hands out no drawables) doesn't freeze the game for the layer's one-second timeout; while the window is occluded nothing is presented. `BOOT_KEYS` steps `unfocus:N` and `hide:N` test this in scripted runs.

- `NFS_AUDIO_LIMITER=on|off` (default `on`; F10 Audio > Peak limiter, live): linked six-channel look-ahead peak limiter on the game mix (-1 dBFS, <= 2 ms look-ahead = 88 frames at 44.1 kHz, 150 ms release), hooked at Snd's float->int16 converter `00825957` (`audio_limiter.c`) because the guest hard-clips there, before the host clamp; the host adds only an instant linked bound after resampling. Movies bypass it (`movies.c`); Off is byte-identical to before. perf.tsv/stats `limit_samples` counts limited samples next to `clip` (X360 mix pursuit: clip 0, 2.15 M limited samples = ~8 s of 150 s). Offline proof: `host/audio/build.sh` (limitertest, limiter_guest_test, each with a broken variant).                                                                           
- `NFS_AUDIO_LAUNCH_REOPEN=0|1` (default `1`): once per process, request one output/encoder close and background reopen, through the Audio menu's path, starting 1.5 s after the first successful bitstream open (TrueHD/MAT, Dolby Digital or DD+). This is a workaround for silence after a quick quit/relaunch while the HDMI/eARC receiver may still be relocking; the port cannot read its lock. The delay exceeds the 0.5 s host health window and the recorded ~1 s startup, but is a starting value for the physical TV/receiver check, not a measured receiver settle time. Guest cursor polls trigger it only in the unpaused startup front end; a paused/loading poll skips it, and a first poll after 5 s expires it. PCM/null outputs are unchanged. Startup device recreation carries the timer across healthy parked-output reuse; later loads cannot rearm it. Set `0` to disable. One always-on `audio: launch reopen done|skipped:<reason> after <ms> ms, format <fmt>` line in `NFSMW.log` records the result; `done` measures completion (including the background open), not just the 1.5 s request delay. A failed open uses the existing output-loss recovery and never rearms the launch action. Reopening may briefly interrupt sound; whether it fixes the physical link remains unverified. The fake TV should see two sequential TrueHD outputs when enabled, one when disabled, with all ordinary device recreations still reusing the current stream.
- `NFS_AUDIO_LATENCY=<frames>` (user-facing tuning): sets the output queue target; default automatic: TrueHD 4096, DD/DD+ 3072, PCM/stereo/null 1024 frames; positive values override it.
- `NFS_AUDIO_RATE=<Hz>` (user-facing tuning): fixes the mix rate; default 0/automatic follows the game for PCM/stereo (initially 48000); Dolby outputs require 48000 Hz.
- `NFS_AUDIO_TEST_DROP=<seconds>[/<failed-opens>],...` (test-only; default no drops): simulates output loss and failed reopen attempts; `0/N` fails N opens at creation.
- `NFS_DSOUND_LOG=1` (test-only; default unset/off): enables verbose host DirectSound logging; any set value enables it.

## Shader compiles

Shader source compilation (`render.m`, 2026-10-28): device creation queues the embedded effect shaders, their material variants and common fixed-function variants on four worker threads, then joins them **before the first scene frame**. Identical MSL shares one in-flight library; unused binding options are canonicalized without changing generated source. The tradeoff is more work during initial device loading. Later misses always compile on worker threads, including FE/loading: unexpected base misses may wait for that shader alone, with **1 ms total per frame**, then defer if still pending. Optional variants retain the compiled base draw, including Carbon lamps. `NFS_ASYNC_SHADERS=0` no longer enables synchronous source compilation. Ordinary draw-time PSO builds and static-pass libraries retain their existing paths; grass PSOs keep their existing asynchronous/PC-fallback path (`NFS_TEST_GRASS_SYNC=1` is the synchronous control). No binary archive was added.

`USERDATA/shadercache.bin` remains bytecode/options/variant history across runtime rebuilds; Metal libraries are recreated at load. Legacy records remain readable, and AUX/soft-smoke records no longer stop the reader and lose all later coverage. Deleting the file is safe. `NFS_TEST_FX_EPOCH=<n>` still seeds the 64-bit effect stamp. `BOOT_DIAG` logs cumulative `shader_compile: frame_sync=N`, `preloaded` and `load_ready`; these counters/logs cost nothing when diagnostics are off. `runtime/compilehitch_test.py` runs without a GPU: frame-thread compile requests **0** vs synchronous mutant **1**; cache records **6** vs broken reader **1**; four identical sources compile **once** vs broken sharing **four** times; readiness/normalization mutants also fail. **1,728 translated MSL comparisons are byte-identical.** `--diag <dir>` rejects frame-thread source compiles or hang/stall reports: the actual baseline fails and fixed race/menu runs pass.

## Settings (registry)

The game's key (`HKLM\Software\EA Games\Need for Speed Most Wanted`) is kept in `USERDATA/registry.txt` and rewritten on every `RegSetValueEx`. With no `FirstTime` value the game runs its hardware detection on the first launch (the reported GeForce 7800 GTX and the 3 GHz CPU rate performance level 4: visual treatment, reflections, car environment maps, world LOD 2, 800x600) and saves it; the options menu changes persist. Delete the file to detect again. `BOOT_REG=name=value,...` overrides DWORD values for one run without saving (e.g. `BOOT_REG=g_RacingResolution=3` for 1920x1080; see Widescreen). On a first run (a fresh `BOOT_USERDATA`) the game skips its settings loader and detects the hardware twice, inline in WinMain before the window and device exist (performance level 4: `g_FSAALevel` 1, `g_RacingResolution` 1) and in `Default__13VideoSettings` (FUN_006c1990) once the device exists; both used to overwrite `BOOT_REG` values, so tests silently ran other settings. After each detection the game's loader (FUN_006c1c00) now reads the `BOOT_REG` values again (`d3d9.m` `first_run_settings`, hooks 006C27D0 in `widescreen.c` and 006C1990), and the port's first-run defaults (                                                               : 4x MSAA `g_FSAALevel=2`, `g_ShadowDetail=2`, the display's native resolution, at most 4K) replace what detection picked unless `BOOT_REG` sets that value; a saved setting always wins (the game's loader reads it); stderr has `boot: first run, WinMain|video defaults: detection picked ..., using ...`. `BOOT_USERDATA=<dir>` uses another folder for saves, settings and the shader cache (scripted runs that create aliases or change options).

## Save commits and offline regression checks

Guest save/profile writes under `USERDATA` (`BOOT_USERDATA` in tests) use a unique sibling
`<filename>.nfs-save-*` file. The destination changes only when the last writable guest handle closes:
fsync the staged data, close, then rename over the old file. FlushFileBuffers really fsyncs;
SetEndOfFile truncates at the current position. Non-truncating opens preserve the old bytes, and
compatible shared opens see the staged file with independent positions. Other guest paths keep direct writes.
A failed write/flush/commit preserves the old destination. An interrupted process can leave a sibling temp file.

                
                                                                              
                                                                                                             
                                                                                                         
                                                                                                              
                                                                                                                                                                                                                                                                                                                                                                                                                                                                  
                 

                
                                                                                                            
                                                                                                   
                                                                                                          
                                                                                                            
                                                                                               
                                                                                                        
                                                                                                                    
                                                                                             
                 

## Antialiasing (MSAA)

Video options > Antialiasing (`g_FSAALevel`) offers the sample counts the Metal device supports: 0 = off, 2 = 4x is the first-run default since 2026-10-20 (detection would pick 1; overridden after both detections, see Settings), 1 = 2x, 2 = 4x, 3 = 8x on the measured host (start-up prints `antialiasing levels`). `BOOT_REG=g_FSAALevel=N` sets it for one run. The CreateDevice log line shows the game's level, its menu maximum (`0x901890`, from `CheckDeviceMultiSampleType` minus 1 and the vendor/caps table in FUN_006d2100, which never lowers it for the reported GeForce) and the MultiSample type/quality it asked for. Checked 2026-10-20: level 2 gives 4x (race and front end starts), level 3 gives 8x (1080p race: 146 MB, 3.45 ms GPU, 120 fps cap), menu maximum 3. The back buffer, the auto depth buffer and render targets the game creates with MultiSample render into 2DMultisample textures; a resolve pass updates the single-sample copy when something reads it (the scene StretchRect, Present, the X360 chain's DOF depth): 2-3 per race frame. Memory at 4K: 2x 146 MB, 4x 292 MB (back buffer + depth). GPU cost at 4K, back to back with other sessions' games competing (absolute numbers inflated): off 18.6 ms, 2x 21.8 ms (+3.2), 4x 23.5 ms (+5.0) per frame; an uncontended 4K 4x race ran at the 120 fps cap with ~8 ms of GPU. With `BOOT_DIAG`, `stats.log` has `msaa Nx (MB, resolves)` and draw dumps list `msaa resolve:` lines; `render_msaa_samples()` gives the current level to the overlay. Alpha-tested foliage isn't smoothed (MSAA covers geometry edges; `run_shots/50`).

`zone`/`loaded` are the car's drivable section and the same scenery-header presence test used by `detail:`. `packs` independently walks the collision grid cell at the actual body position, reporting each distinct referenced section and its collision-pack pointer presence (`:0` absent, `:1` present, `:-1` invalid). `none` means no cell references; `unknown` means unavailable; `truncated` means the 32-pack/4096-reference bound was reached. 6 of 9 guarded race runs started 14:08-14:20 with three concurrent games running had no frame after frame ~110 (the
cars' first loads: race 15.1.1 creates the car sim tasks at frame 107), the game thread in `CarLoader::ServiceLoading`
(0075BED0) -> `RealFile::GetInfoFastByName` (007EE073); reruns were clean and the reports are gone. Same window: main's
recompiler output was rebuilt (14:13, `8cd5eca`), so the machine was also compiling on every core.

What that call does (decomp, `speed_007e0e90.c`): `bFile::OpenLowLevel` (0064D600) asks for a file's size;
`GetInfoFastByName` finds the device (`FILE_nametodevice` 007EDCA5), opens the name under each search location
(FUN_007EDD78; a device used for the first time starts its background thread there, FUN_007ED751, and waits for its ready
event), takes the size and closes (`iCloseFileSysHandle` 007ED545, which locks the file system's handle mutex at
`gpFileSysInfo+0x34`). It is synchronous on the calling thread: no loop and no wait on another thread except those
two (the device-start event and the handle critical section). The port side: `CreateFileA`/`ReadFile`/`GetFileSize`/
`CloseHandle` are plain blocking POSIX calls under the GIL (`boot.c`, `ReadFile` ignores OVERLAPPED; the game's
reads pass none), names resolved case-insensitively under the game folder.

**Nothing writable is shared between two runs:** a race run writes only its `BOOT_USERDATA` (registry.txt, shadercache.bin,
app.txt, saves) and its `BOOT_DIAG` dir; the game opens every file in the game folder read-only (all `CreateFileA` of a
race run: access 80000000, disposition 3), the X360 extract is read-only, logs go to `<diag>.out` (the app's
`~/Library/Logs/NFSMW-port` log is claimed per process with a lock file), and there are no fixed temp names, named
kernel objects (all are in-process: `threads.c`) or shared caches. Only the GPU, the Metal compiler service and the CPU
are shared.

**Tries that did not hang (41 runs, 0 hang or stall reports):** 4-way concurrent starts x4, 6-way x2, 4-way under 18
busy cores, 4-way during a full `build_all.py` (18 cores), 3-way at 60 Hz and at 120 Hz, 3-way with

## Display changes mid-run (`user32.m` display_poll, `widescreen.c`)

The main display can change under a running game (a TV waking, mirroring). `NSApplicationDidChangeScreenParametersNotification` marks it; 0.7 s after the last one (a debounce for the burst), and not while the F10 menu is open, full screen windows re-fit the screen. If the game is on the native resolution (and `g_RacingResolution` isn't a BOOT_REG override, Options not mid-edit), the resolution list is rebuilt for the new display and the game's own resolution change runs (`LoadedFlagMaybe` 982C39: eDisplayFrame resets the device at the new size). A resolution picked in Options stays. Log: `boot: display changed`, `boot: native resolution A -> B`, then the new swap chain. Test: `NFS_TEST_DISPLAY_CHANGE=<secs>:<WxH>` (with `NFS_DISPLAY_PIXELS` for the start size) pretends the display became WxH pixels after that many seconds.

**Engine sound (`posaudio.c`, 2026-10-25; default Realistic):** F10 Audio > "Engine sound" / `NFS_ENGINE_SOUND=retail|realistic` (live). Retail: the player engine is one full-gain point that `SFXCTL_3DRearPos::UpdateParams` 004E5A80 puts 2 m behind the car centre in the hood/bumper cameras for every car, so 5.1 plays it from SL+SR only (chase camera: C only). Realistic changes only the pan of the player's own Ginsu engine voice (CARSFX_GinsuEngine 004EE3E0 whose CSTATE, +0x14, is the Rear Car Pos controller's): the engine sits at the car's real layout (table `kEngineCars`, keyed by the pvehicle collection key at `EAX_CarState+0x200`, Collection+0x20 = Attrib hash of the name; unknown cars keep the 2 m-behind point) relative to the camera (2D position/facing at 009144A0/009144C0 per view, the same inputs as `SetCameraAngle` 004B5D70), spread over an arc by its apparent size, plus a 10 % diffuse share, scaled to the retail gains' power. The controller output the mix map reads stays retail (its level curves depend on angle and distance), so loudness is unchanged. **Soundstage (same Engine sound switch):** Realistic also spreads AI racers' and cops' engines (CARSFX_GinsuEngine / CARSFX_AEMSEngine), traffic engines and cop sirens. How the game pans a source: the 3D controller (`SFXCTL_3DObjPos::GenerateSinglePlayerMix` 004B5E50, the player's `SFXCTL_3DRearPos` 004E5A80) writes a camera-relative azimuth and distance, the mix map turns them into the object's input words (`**(obj+0x10) & 0xFFFF` is the angle), the object hands the angle to Snd: the Ginsu engines synchronously (`_SND3dpos` in 004EE820/004EEA00), traffic/siren/AEMS engines through a Csis member block that the AEMS script reads later on the Snd thread (`SNDAEMSI_bankazimuth` 0081A0AC, FUN_0081F207 caller 0081A0D1; music/NIS streams `_SNDSTRM_setazimuth` 0081CF56), and `FUN_0081FE64` turns the angle into five gains. Realistic changes only that last step for these voices: the gains become the panner's average over the arc the car subtends at its distance (engine at its layout offset, siren on the roof; power of the game's gains kept), and the asynchronous voices are matched to their source by the angle word (a match whose angle is further from the source's recomputed azimuth than 3 deg + 1 m of travel is left retail). Retail, mix maps, levels, music, ambience and every other sound are untouched. BOOT_DIAG: `soundstage:` per second (registered/matched voices, spread/skipped/rejected, the azimuth gap, and per class player/ai/cop/traffic/siren/bank/stream/other the mean speaker shares and how many updates reach C / SL+SR) and `soundstage-callers:` (the pan call sites outside the source hooks). Offline test: `runtime/posaudio_test.py` (Retail byte-identical for AI/cop/traffic/siren, async matching, nine broken variants fail).
**Audio-loop watchdog (`dsound.c`, always on):** a looping stream (Play with DSBPLAY_LOOPING, >= 16 KB, written at least 4 times) whose play cursor travels one full buffer while no Lock/Unlock write happened for over 1 s and the game isn't paused writes `audio_loop_N.txt` into the session folder (stream state, Snd thread and every guest thread's wait, the last 32 buffer operations) plus one `audio: loop watchdog` line (NFSMW.log, session.txt); at most 3 a run. Checked once per 250 ms from the per-frame pass (so a stuck Snd thread cannot silence it); per buffer operation it adds one tick and a counter. `NFS_TEST_AUDIOLOOP=<s>` (test only) refuses Lock/Unlock of the watched stream from <s> seconds on, which makes the cursor cycle stale data. BOOT_DIAG: `dsaudio watchdog checks= fired= max_quiet_ms=` and one state line per watched stream.

**Asset-root manifest (`roots.h`, `<userdata>/roots.txt`, public-release M1b):** one file tells the game where the player's files are: `pc_root`, optional `x360_root` (raw extracted X360 files), `assets_root` (Setup-converted `hd_textures_mips_alpha`, `hd_textures_ui`, `nis_arrest`), `movies`, `caches`, `tmp` (`NFS_ROOTS=<file>` names another manifest; `NFS_*` switches still win).
