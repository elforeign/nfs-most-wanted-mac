# Game controller (part 1 of 2)

Part of the runtime documentation; the index and switch lookup hint are in `runtime/README.md`.

## Game controller

| F10 Controls setting (`app.txt` id) | Switch | Default | What it does |
|---|---|---|---|
| Steering dead zone (`controls.steering_dead_zone`) | `NFS_STEER_DEADZONE=pc\|x360` | PC (none) | X360 changes only the two continuous steering lows in Type 1 `drive_analog` (`AD37E45A`) to the X360's dead zone, generated from the player's ATTRIBUTES.BIN (`X360E_STEER_LOW_WORD`); `clamp((u-low)/(1-low),0,1)`. Other control types, pedals, TURN edges and the separate keyboard records retain their PC data; binary keyboard/button steering remains 0/1. Applies to the current steer bindings, including remapped analog axes. **Restart required**: attributes load at startup. Independent of X360 Game Data. `BOOT_DIAG` emits one `steering_deadzone:` line with option, record, matched/patched counts and low value/bits. Offline proof: `"$TOOLS_PY" -I recomp/steer_deadzone_test.py` (retail PC/X360 assets required); the wrong-offset mutation must fail. User to judge feel with a physical pad. |
| Steering response (`controls.steering_response`) | `NFS_STEER_RESPONSE=retail\|medium\|linear` | Retail | Rewrites the 21 points of the game's steering remap (SteerInputRemapTables table 0, data 008F8B80, used only by DoHumanSteering 0069E820 at 0069E8F2; the X360's is identical): Retail = the game's (half stick = 15 % of the speed's max lock), Medium = each point halfway to the input, Linear = output = input. Max lock by speed and the rate limit stay the game's; AI cars and 0/1 keyboard steering are unaffected. **Live** (applied by the DoHumanSteering hook). `BOOT_DIAG`: `steerresp:` lines (mode written; input -> table output as the stick moves, 40 max). Offline proof: `"$TOOLS_PY" -I runtime/steerresp_test.py` (Retail = the exe's table exactly; `--broken` fails). User to judge feel. |
| Control type (`controls.control_type`) | `NFS_CONTROL_TYPE=1..10` | 1 | The X360's Control Types (`controltype.c`                                                                     ). 1 keeps the port's bindings; 6 is 1 steering with the D-pad only; 2-5 / 7-10 move the driving controls as the X360's variants 2-5 by position (A Cross, B Circle, X Square, Y Triangle, White R1/RB, Black L1/LB, L/R L2/R2 or LT/RT, right stick, R3, Back Create/View), with the X360's 0.46 right-stick pedal ramp on 5 / 10. Applied on the controller slots each frame (`FUN_006349B0` hook): keyboard, the Controls screen and the saved bindings stay the user's; PlayerSettings stays Type 1 (no career profile change). Non-PlayStation pads get their physical buttons while driving for variants 2-5 (`user32.m`). Live. `BOOT_DIAG`: `controltype:` lines (type, each overridden action on/off with its value). Offline proof: `"$TOOLS_PY" -I runtime/controltype_test.py` (PASS, 120 checks; broken table or type index fails). |
| Triggers (`controls.triggers`) | `NFS_TRIGGER_LAYOUT=shift\|pedals` | Shift | Native PlayStation pads: Pedals overlays R2 gas, L2 brake/reverse, Cross shift up and Square shift down after the Control Type preset. Other actions, keyboard and saved bindings stay intact. Shift restores the saved bindings (PS2 by default). Live; diagram labels and adaptive trigger roles follow the effective preset. Pedals adds no deadzone: the game already snaps below 5% / above 95%. |

`dinput.c` exposes the first GameController.framework extended gamepad (DualSense, DualShock, Xbox, ...) as a DirectInput gamepad laid out like the 2005-era "Controller (XBOX 360 For Windows)": X/Y left stick, Rx/Ry right stick, **six axes from the first enumeration: LT on Z and RT on Rz, independently**, 12 buttons, D-pad as POV. Triggers encode release/half/full as 32768/49151/65535 in the default 0..65535 range (custom DirectInput ranges are preserved); release is the centre of a positive half-axis. **Connect a controller at any time** (asleep at launch, plugged in or reconnecting later, swapped for another): the game enumerates its devices once at start-up (FUN_006dc540), so its gamepad is always there from start-up, read centred and named after the Xbox 360 pad until a controller connects; the first one to connect then takes it over live (its name, layout, binding set, glyphs and rumble), and pad prompts switch to it. A controller that goes away reads centred, nothing pressed (DIERR_INPUTLOST would have left the game holding the last state: `FUN_007f28a4` keeps it on an error). The app log says `boot: controller connected: ...` / `boot: controller disconnected ...` / `boot: no controller connected yet ...`. Start-up still waits up to 0.5 s for GameController discovery, so a pad already on names the gamepad from the start. The game's PC defaults for it (Options > Controls, controller page, all remappable): Accelerate Button 1, Handbrake 2, Brake 3, Speedbreaker 4, Look Behind 5, Reset 6, N2O 7, Pause 8, shifting/camera unbound, D-pad for Engage Event / Blacklist / World Map / SMS.

**PlayStation pads, native** (`padbind.c`, `dinput.c`                                                              ): a DualSense, DualShock 4 or DualSense Edge is detected automatically and given to the game as itself: the Controls screen's joystick page is titled "Controller (DualSense)" ("Controller (DualShock 4)", "Controller (DualSense Edge)"; any other pad shows its own name, e.g. "Controller (Xbox Wireless Controller)") and every control is bindable in the game's own remap UI under PlayStation names: Cross Circle Square Triangle, L1 R1, L2 R2 (analog: each is one axis half), L3 R3, Create (Share), Options, PS, Touchpad, the D-pad, both sticks per direction (Left Stick Up, Right Stick Down, ...), the Edge's paddles. No hard-coded mapping: the game's binding table drives the car and the menus. Defaults = the PS2 layout below (the Xbox 360 defaults translated through what the PlayStation layout did, plus right stick gas/brake, R3 speedbreaker, R2/L2 shift, which now need no binding); menus keep ✕ accept, △ back, ○ □ Create Options for the console prompts; the PS button and the touchpad click are bound to nothing; they reach the game (bindable) unless one is the F10 menu's shortcut (F10 > Controls "Controller: open this menu": by default the touchpad click). Reset to defaults on the page gives them back. The PS button belongs to the game while it is frontmost (no Launchpad). The Controls screen's own keys work from the pad: Circle = Defaults (key 1), Square = Clear (key 2), Triangle = Done. Each controller type (the pad's name) has its own binding set per profile: the game's profile keeps the active one, `USERDATA/pad_bindings.txt` all of them (written at each profile save and type change), so a profile loaded with another pad, or a pad of another type connected while playing, brings that type's own set (or its defaults) back; a profile saved before this counts as the Xbox pads' set. Glyphs: PlayStation art with a PlayStation pad whatever the Controller menu says; the controller-diagram loading screen's labels follow the bindings. The Controller menu's layouts below apply to Xbox and other pads only. `BOOT_DIAG`: `bindings.txt` (the table at each defaults / profile load / save / type change / bind capture), `padbind:` lines in events.log (the Controls actions' values as they change, captures, type changes), `pad: identity` lines.

The Controller menu or F10 Controls > Button layout (PlayStation Layout / Xbox Layout, saved as `pad_layout` in `USERDATA/app.txt`, applied at once) or `NFS_PAD_LAYOUT`, which overrides it, picks (with no pick, the active pad's own console: PlayStation for a PlayStation pad, Xbox for every other pad, following hot-plugs and pad swaps live; the F10 row shows the layout in effect, and its reset returns to the automatic choice; `BOOT_DIAG` `pad: layout` lines say which and why) how the physical buttons reach those while driving (`user32.m` `pad_apply_layout`), so that the PC defaults give each console version's layout from its manual:
- `playstation` (PlayStation pads' default, PS2 manual): ✕ or right stick up gas, □ or right stick down brake/reverse, △ look back, ○ or R3 speedbreaker, R1 e-brake, L1 nitrous, R2/L2 shift up/down, Create reset car, Options pause.
- `xbox` (other pads' default, Xbox manual): right/left trigger gas/brake, A e-brake, B nitrous, X speedbreaker, Y look back, RB (the Black button) change camera, right stick up/down shift, Back reset car, Start pause.

For non-PS pads, Xbox layout now defaults Accelerate to Rz+ `(7,0,2)` and Brake to Z+ `(5,0,2)`, retaining each physical pressure (half travel = half demand, including both pedals together). PS2 layout keeps Button 1/3 face/right-stick gas/brake, removes the obsolete combined-Z pedal halves, and defaults trigger shifts to Z+/Rz+. Trigger shift button aliases are suppressed during remapping so capture records the axis. Xbox right-stick shifts still send Buttons 9/10, and camera Button 11; these remain available to bind: bind them once in Options > Controls (press the layout's shift/camera control in the binding field). In menus and the pause menu the buttons are the console version's, matching the console prompts: PlayStation ✕ accepts, △ goes back, ○ / □ / Create / Options do what the CIRCLE / SQUARE / SELECT / START prompts say (the PC keys 1 / 2 / 3 / 4); Xbox A, B, Y, X, Back, Start the same way; L1/R1 (LB/RB) the tab arrows. The PC's own front-end mapping had Button 2 accept, Button 3 go back, Button 1 do key 1 and no pad button for keys 2-4 (so on a real Xbox 360 pad B accepted); keys 2-4 now go in as DirectInput key presses from the pad (`user32.m` `pad_apply_layout`). Menus are told from driving by the FE package in control (the race results come up while the sim runs). **Re-mapping in Options > Controls:** while the game waits for the input to bind (the input object at `IOModule` 0x920DE0 +8: +0x183C, device +0x1840 = 3; set by `FUN_00628C00` when a field is picked, cleared by `FUN_00634900` when it captures), the controller sends the driving mapping, so a binding records what the button does while driving (✕ = Button 1, the Accelerate default), the right stick is only its axis (Y Rotation), and a button held when the wait starts (the ✕ that picked the field) or ends is ignored until released. Before this (2026-10-20, padprompts until padgas) a field bound with ✕ got Button 2 (✕'s menu Accept) and the game cleared the action that had Button 2 (Handbrake); ○ gave Button 1 (key 1 in menus). The user's profile ended with Accelerate = Button 2 and Handbrake = Button 1, so ✕ and right stick up (both Button 1 while driving) pulled the handbrake. Such a profile needs its controller fields re-bound (Accelerate ✕, Handbrake R1, ...) or the controller defaults restored.

Binding persistence is now v2: `USERDATA/pad_bindings.txt` starts with `# NFSMW pad bindings v2`, and each key includes `native_ps`, `nonps_ps2` or `nonps_xbox` along with profile/name hash. Changing a non-PS layout saves the old variant and loads the selected variant even with the same pad name. Only legacy non-PS records are migrated on first use: old combined-Z gas becomes Rz+ in Xbox mode (brake stays Z+); PS2 mode removes those pedal halves. Exact original default action pairs get the new defaults; other custom button choices survive. Old rows remain under `legacy`, and the original sidecar is retained byte-for-byte as `pad_bindings.txt.v1` before the first migration write. Native PS values/name hashes are never converted; a no-op load or swap does not rewrite the sidecar. Profile-only legacy sets follow the same path; a known v2 set is never reclassified as legacy when loaded with another pad. Normal profile saves/type or layout swaps persist changed binding sets.

**Front-end items** (`fe_console.c`): the main menu hides LAN Play (`MainLAN`) and Online (`MainOnline`, dead service) by default, as on the X360: the menu builder's `IconScrollerMenu::AddOption` (00573960) skips those two items; `NFS_LAN=1` restores only MainLAN (experimental, full flow PENDING); the legacy `NFS_FE_ONLINE_ITEMS=1` restores both when LAN mode is off. Options > Audio has no Audio Mode row (Mono / Stereo did nothing: the port always outputs discrete 5.1; the Audio output menu is the control): `UIWidgetMenu::AddToggleOption` (00588570, hooked) skips the `AOAudioMode` widget; `NFS_FE_AUDIO_MODE=1` puts it back. The game's controller-unplugged pause (`IOModule::CheckUnplugged` 00644E40 -> `ControllerUnplugged.fng`) works: the pad class's "is connected" (`InputDevice::IsConnected` 006287D0, hooked) reports gone when the controller that was the active input is gone (`padprompts.c prompts_pad_lost`; keyboard-only play never, a key or mouse move clears it); `BOOT_PAD=sim:dualsense@2-40-70` (connect at 2 s, unplug at 40, connect at 70) shows it in a race; the screen carries the X360 text (54EE7FA6, via `fe_console_search`, the text-swap table in front of `SearchForString` 0056BB80). The same swap table also gives the save text without the PC's extra warning sentence (F18) and the Video > Advanced labels " (set by port)" while the X360 post chain is on (F14). The mouse pointer is hidden whenever the controller is used (`user32_hide_pointer`, `setHiddenUntilMouseMoves`; the first mouse movement brings it back). `BOOT_DIAG` logs `fe_console:` lines.

**Button prompts** (`padprompts.c`): while a controller is the active input (the last button, stick or D-pad input came from it, or one was found at start-up), menus and the pause menu show the console glyphs every package carries (flag 0x40) instead of the PC keycaps (flag 0x8), as the X360 does; a key press, click or mouse movement brings the keycaps back, live. A package with no console set at all (Options > Video, Controller: PC-only screens) keeps its 0x8 objects drawn (Advanced, Back, Accept, Defaults) and draws each `PC_KEY_*` keycap image as the console glyph it stands for (ESC = Triangle/B, 1 = Circle/Y, 2 = Square/X, 3 = Select/Back, 4 = Start: the Controls screen's Done / Defaults / Clear hint bar shows them, PlayStation or Xbox art by the layout as in the other menus; `padprompts.c` `mark_keep`, decided when the package loads; `BOOT_DIAG` logs each as `prompts: <package> <id> kept|keycap hidden`). Objects flagged 0x44 (online icons) don't count as a console set. PlayStation layout: PlayStation glyphs the port draws at start-up (64×64); Xbox layout: the X360's glyph art from the player's X360 `GLOBAL/GLOBALB.BUN` (without it the Xbox layout keeps keycaps). `NFS_BUTTON_PROMPTS=auto` (default), `=console`, `=pc` (the original code, untouched). With `BOOT_DIAG`: `prompts.txt` (every loaded package's flagged objects, their textures and whether the PC packs have them, and the FE input mapping), `prompt_*.png` (the glyph art), `fepad:` lines in events.log (each FE pad event: which action a key or button gave), `pad: driving/menus` lines. Scripted pad input for tests: `BOOT_KEYS` steps `pad:MASK` (physical buttons, as `BOOT_PAD` `buttons=`), `padraw:MASK` (the game's DirectInput buttons), `padaxis:lx=1` (one axis; a stick also goes through the layout, like a real one), each held 6 ticks or `:N` ticks (`pad:1:600`), with `BOOT_PAD=sim:...`. `pad:` lines in events.log give the game's DirectInput buttons after the layout, the mapping in use (`driving`, `menus`, `remap`) and the FE package in control; each change of mapping also logs the game's controller bindings (`pad: controller bindings`, action: type/index of the primary and secondary binding, from `GameAction` 0091F418; type 2 index n = Button n+1).

**Controller-diagram loading screen** (`padprompts.c`): X360 loading tip 0x1B (`Loading_Controller.fng`). While a controller is the active input the tip picker (`GetARandomTipScreen` 0056ADA0) also offers it; its package is filled in when it loads (the PC never builds the screen: ctor `0058F070` has no callers): diagram image 0x922A39C4 = the X360 pad (`EC3C0443`/`44`, Xbox layout) or the PS2 DualShock (`DF7B27A7`/`A8`, PlayStation layout) streamed from `DYNTEX.BIN`, callout labels per slot (CButton_k / BUTTON_k, k = 1..17; the PC's table `0091D278` is zeroed). Xbox layout: the X360's table (`828FFBB0`, `callout_labels`, controller configuration options `+0x88`), the bumper "Look Back" callout (slot 12) hidden because LB is unbound here. PlayStation layout: `ps_labels`, what each control does in `user32.m pad_apply_layout`: slots 1/3 the shoulder lines L1 nitrous / R1 e-brake, 4 triangle look back, 5 circle speedbreaker, 6 cross accelerate, 7 square brake/reverse, 12/13 the L2/R2 rows shift down/up, 14 Create reset car, 15/16 right stick up/down accelerate/brake, 17 Options pause, 8-11 the D-pad's own game actions (unchanged); "Xbox Guide" hidden. The DualShock art has one line per shoulder, so L1/R1 sit on them and L2/R2 in the rows below. Keyboard/mouse keeps the PC behaviour (tip not picked). `NFS_LOADING_CONTROLLER=off` keeps the PC everywhere; `NFS_TEST_LOADING_TIP=0x1B` (test only) forces the tip. `BOOT_DIAG_STRINGS=1` (with `BOOT_DIAG`) writes `strings.tsv`: hash and text of every string lookup (`SearchForString` 0056BB80; the label hashes are not recoverable from `LANGUAGES/*.bin` offsets directly).

**Wide chyron** (`widescreen.c`): the front-end song banner (`Chyron::Start` 0058D670) uses `WIDESCREEN_MODE` from the first menu on wide screens, as the X360 (options `+0x34` set before it starts, not only by the race HUD). `NFS_WIDE_CHYRON=off` keeps the PC. BOOT_DIAG logs `chyron:` lines.

**Speed-reactive chase camera** (`chasecam.c`): F10 Controls > Camera, **Speed-reactive chase camera**, Off / On; default **Off**, live, `NFS_CHASE_CAM=off|on` (`controls.chase_camera`). Only player close/far chase views change. The decoded speed curves add 0–37° / 0–47° to MW's own FOV (78° / 90° at rest), multiply MW's lag and height by the decoded position/height ratios, and apply the close direction-duration ratio (1→0.5 by 80.47 km/h; far constant) to MW's rest direction durations. MW's existing distance boost and direction taper are replaced while On; its vibration, eye/target smoothing, FOV smoothing and other cameras retain their existing code. No shared camera attributes/tables are rewritten. `runtime/chasecam_test.py` checks curves, actual translated parameter/boost evaluators and Off delegation, rejecting broken curve and Off controls. With `BOOT_DIAG_CHASE=1`, `chasecam.tsv` records target FOV, applied lag distance, height, direction duration, actual FOV and exact matrix words. `BOOT_DIAG_CHASE_COMPARE=1` replays sampled settled-POV camera updates from identical saved inputs through raw retail and Off hooks, recording both matrices/FOV in `chasecam_compare.tsv`; `=broken` deliberately offsets one output matrix word by 0.25 in the second pass (also exercised offline, 0 differing words normally / 1 when broken). For proof captures only, `BOOT_DIAG_CHASE_CRUISE=50|200` caps the human AI's requested driving speed (55 / 200 km/h respectively; physical car speed remains measured), and requests one shot after sim 16 s and half a second within 5 km/h, with at most 0.81° total heading change and FOV within 1° of target.

**Rumble:** the X360 version's model (`feedback.c`), with the game's "Rumble" option (Options > Controls). LocalPlayer::DoFFB feeds the player's IFeedback every sim tick (per wheel: slip, skid, speed with the road surface; shift kicks, nitrous, engine damage, gear changes) and OnCollision on contacts; on PC those methods were empty stubs and any DirectInput pad took the steering-wheel branch instead, so the hook on DoFFB (006EE490) runs it without the wheel, as on the console. Oscillators from the surface's rumble curves (the same data as the X360's ATTRIBUTES.BIN) and event envelopes make a heavy (left) and a light (right) motor level, 0..1, combined and scaled exactly as the X360 sends them to XInput. Every tyre reads the surface under it (`BOOT_DIAG` writes all 47 surfaces' curves to `surfaces.txt`): asphalt, cobble, concrete, wet road, metal and the like only have the wheelspin (slip) curve, so they rumble on burnouts; grass, grass shoulder, dirt, gravel, sand, mud, snow, hay and golf add a speed hum (from 5 m/s, with 1 and 4 Hz pulses); wood/organic pulse instead; a blown tyre counts as dirt; no surface has a skid curve. All on the heavy motor; the light motor comes from events. Opening F10, pausing the game, losing window focus or deactivating the app posts zero to both motors immediately and suppresses further rumble until every hold clears (the game's Sim pause state is checked each main-loop pass, pad read and feedback resume). Closing/resuming discards the old oscillators and event envelopes; only the game's next feedback update can rumble again. The HID queue also gates pending reports, so pad reads or reconnects while held cannot restore old levels. The motors also stop when the game quits (Quit, exit, SIGTERM/SIGINT), and reports go out on their own queue, never blocking the game thread. Collisions use the X360 strength: how much the contact changed the car's velocity (scrapes are light, crashes full), with the port envelope changes below. The pad reports no DirectInput force feedback. `rumble.m` plays the levels on a DualSense (USB or Bluetooth) through its compatible-vibration mode, an HID output report (CoreHaptics through GameController.framework refuses unsigned processes). Other controllers don't rumble yet. `NFS_RUMBLE=off` leaves the controller alone (scripted or unattended runs; the model and its diag lines still run). With `BOOT_DIAG`, `feedback:` lines give each suppress/resume transition (reason, remaining hold mask, motors zero), each second's calls, the per-wheel inputs and each source's motor level. Offline regressions: `feedback_test.c` checks immediate stop, continued game updates while held, overlapping menu/pause/focus/app holds and fresh feedback after resume (29 checks; pre-fix model with missing hooks: 19 failures); `rumble_test.m` intercepts HID writes to check USB/Bluetooth queue suppression, resume and `NFS_RUMBLE=off` without opening a controller (15 checks). Compile/run commands are in their headers; both pass under AddressSanitizer/UndefinedBehaviorSanitizer.
