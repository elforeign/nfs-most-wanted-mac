Other switches: `BOOT_KEYS=frame:KEY,...` or `BOOT_KEYS=seq:step,...` (scripted input; steps are keys, `wait:N`, `sim:S` (until race sim time S seconds), `idle:N`, `skipmovies`, `cmdopt:K` (a Cmd-Option menu shortcut, e.g. `cmdopt:p` cycles the overlay), and `unfocus:N` / `hide:N`, which take the focus away for N seconds like Cmd-Tab / Cmd-H; keys are RETURN ESCAPE SPACE BACK UP DOWN LEFT RIGHT F10 TAB or a letter/digit, which is also typed as a character; `race:N` waits until N ticks after the race state began). Creating a career alias: `...,RETURN,wait:300,RETURN,wait:300,LEFT,wait:60,RETURN,wait:300,RETURN,wait:300,RETURN,wait:300,BACK,BACK,BACK,BACK,T,E,S,T,RETURN,wait:300,LEFT,wait:60,RETURN` from the main menu (with `BOOT_USERDATA` pointing at a scratch copy). A path to the Quick Race menu that works: `seq:skipmovies,wait:450,RETURN,wait:400,RETURN,wait:400,RIGHT,wait:120,RIGHT,wait:120,RETURN` (the title takes input once "CLICK to continue" shows; Enter picks the highlighted "No" on the alias dialog). Also `BOOT_SHOT=frame:path.png,...`, `BOOT_TRACE=1` (imports to stderr), `BOOT_HEADLESS=1`, `BOOT_NOFAST=1` (copy all vertex data), `NFS_AUDIO=null|pcm51|stereo|dd|ddp|truehd`. `NFS_X360_MOVIES=<dir>`: where the X360 WMVs are (default: the `movies` or `x360_root` entry of `roots.txt`); a movie missing there (or an empty dir) plays the PC VP6.

`BOOT_NIS=<scene>` (test only, inert without it; `diag.c`): the race's own intro NIS (any `IntroNis..` name passed to `NISActivity::Load` 006F51F0) is replaced by the named scene, so scenes the plain `BOOT_RACE` route never plays (`IntroNisBL12`: Izzy's challenge) can be loaded and inspected; logs `BOOT_NIS: scene A -> B` to stderr. With `BOOT_RACE=12.2.1` it plays Izzy's intro on the 12.2.1 start (the scene's cars land on the road and the `nis:` rows work as below).

                
                                                             


     
                                                                                                                                                             
   


                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                             
                 

`zone`/`loaded` are the car's drivable section and the same scenery-header presence test used by `detail:`. `packs` independently walks the collision grid cell at the actual body position, reporting each distinct referenced section and its collision-pack pointer presence (`:0` absent, `:1` present, `:-1` invalid). `none` means no cell references; `unknown` means unavailable; `truncated` means the 32-pack/4096-reference bound was reached. A cell may contain irrelevant/disabled instances, so a missing pack alone does not establish that the road is missing. Correlate its section number and `ground_fail`, loss of wheel contact and body Y/velocity with `detail: load/loaded/not loaded` and `streaming:` events. Missing relevant packs that become resident as contact/height recover support a residency failure. Continuous relevant residency and successful height queries during the visible fault reject that explanation for the sampled interval. With residency established, discontinuous `anim` versus scene/dt totals suggests timing; smooth dt/cursor but an anomalous `animpos_native`/`query` trajectory at the same scene time suggests scene data/placement. Neither proves a retail-data fault: compare decoded data or a retail capture. If a clock/physics divergence remains, compare equal scene times in separate 60/120 Hz and lockstep runs; one 120 Hz trace cannot prove rate dependence.                                                                                     

## Startup hang in CarLoader with overlapping runs (2026-10-20): not reproduced

6 of 9 guarded race runs started 14:08-14:20 with three concurrent games running had no frame after frame ~110 (the
cars' first loads: race 15.1.1 creates the car sim tasks at frame 107), the game thread in `CarLoader::ServiceLoading`
(0075BED0) -> `RealFile::GetInfoFastByName` (007EE073); reruns were clean and the reports are gone. Same window: main's
recompiler output was rebuilt (14:13, `8cd5eca`), so the machine was also compiling on every core.

What that call does (decomp, `speed_007e0e90.c`): `bFile::OpenLowLevel` (0064D600) asks for a file's size;
`GetInfoFastByName` finds the device (`FILE_nametodevice` 007EDCA5), opens the name under each search location
(FUN_007EDD78; a device used for the first time starts its background thread there, FUN_007ED751, and waits for its ready
event), takes the size and closes (`iCloseFileSysHandle` 007ED545, which locks the file system's handle mutex at
`gpFileSysInfo+0x34`). It is synchronous on the calling thread: no loop and no wait on another thread except those
two (the device-start event and the handle critical section). The port side: `CreateFileA`/`ReadFile`/`GetFileSize`/
`CloseHandle` are plain blocking POSIX calls under the GIL (`boot.c`, `ReadFile` ignores OVERLAPPED; the game's
reads pass none), names resolved case-insensitively under the game folder.

**Nothing writable is shared between two runs:** a race run writes only its `BOOT_USERDATA` (registry.txt, shadercache.bin,
app.txt, saves) and its `BOOT_DIAG` dir; the game opens every file in the game folder read-only (all `CreateFileA` of a
race run: access 80000000, disposition 3), the X360 extract is read-only, logs go to `<diag>.out` (the app's
`~/Library/Logs/NFSMW-port` log is claimed per process with a lock file), and there are no fixed temp names, named
kernel objects (all are in-process: `threads.c`) or shared caches. Only the GPU, the Metal compiler service and the CPU
are shared.
