# X360 renderer features, widescreen, antialiasing, display changes (part 1 of 6)

Part of the runtime documentation; the index and switch lookup hint are in `runtime/README.md`.

## X360 renderer features (`x360.m`, `x360_post.m`, `x360_textures.m`)

Shadow fit (with shadows on, `g_ShadowDetail` > 0): `NFS_SHADOW_FIT=x360` (default: the whole X360 shadow path), `x360range` (only the X360 focus range and angle, otherwise PC), `pc`. Shadows themselves follow the saved `g_ShadowDetail`; first-run default is 2 (unless `BOOT_REG` overrides it; `d3d9.m:558`). `x360` adds, each with its own override:
- the exact X360 LiSPSM light camera (`x360_shadow_fit.cpp`, plan M2: sharper shadows near the camera, `run_shots/31`, `32`, left x360range, right x360), including the X360 low-sun rule (the fit's light is raised to a minimum height; lighting keeps the real sun);
- the X360's larger map (`NFS_SHADOW_SIZE=<n>`, PC 1024; the X360 size comes from the player's default.xex): `GetShadowWidth/Height` (006C86B0/C0) and the textures `FUN_006c8770` creates; ~0.2 ms more GPU, same fps;
- white border on the shadow sampler (`NFS_SHADOW_BORDER=white|clamp`): `render.m` forces BORDER + white on every compare sampler;
- front-face culled casters (`NFS_SHADOW_CULL=front|none`): `FUN_006c68b0` runs with pass mode 3 in the shadow pass, the X360 rule (double-sided materials stay unculled); the changed effect cull modes go back to NONE when `FUN_006e44c0` returns, as PC leaves them.
The texel-centre bias (0.5 + 0.5/size, compiled in at 006E53FC/006E5407) follows the map size in every mode (the bias matrix is patched at its `D3DXMatrixMultiply`, 006E5428). Captures: `run_shots/33`-`35`. Shadow strength is the game's own: FUN_006c83d0 fades receivers to lit with the sun's height (a linear fade over the sun's height range) and with the weather (`1 - Rain+0x290`, which drifts 0-0.5 in 15.1.1 even with `g_RainEnable=0`). Diagnostics for shadows (BOOT_DIAG): the techniques each effect gets per shadow level, the strength inputs every 300 frames, the shadow matrices in `BOOT_DIAG_DRAWS` frames, the sampled depth map as `tex_N/depth_*.png`; `BOOT_DIAG_MSL=1` saves every translated shader as `msl/<key>.metal`; `NFS_TEST_SHADOW_COMPARE=never|always|greater` (test only) forces the compare. `NFS_TEST_SUN_ELEVATION=<deg>` (test only) replaces the time-of-day sun's elevation; every race starts at time of day 0.449 with the sun 62° high, so there is no natural dusk race.

**Shadows probe once failed through its own map (2026-10-20, `run_shots/shadows_probe_border_leak.jpg`):** the probe's forced-shadow frame came out ~5 % brighter (foliage, the hillside, a horizon band, the road under the car's wing: the receivers the real map shadows). Its depth-0 map is 1x1, and the X360 white border (`NFS_SHADOW_BORDER=white`, the default in the x360 fit) turns its sampler into clamp-to-border: linear PCF then blends the one texel with the white border by the distance from the map's centre, up to 75 % lit at the corners, so really-shadowed receivers got lighter. The probe now samples its map through an edge-clamped compare sampler (`sampler_state(..., 2)` in `render.m`): every lookup is in shadow, 64 % of the frame darker, 0.0 % brighter. Not a rendering fault: every receiver that samples the map (467 draws in 15.1.1: world, worldnormalmap, worldreflect, car, particles; no sky or fog) uses the compare result as a lit factor that only adds light (`saturate(s + fade + InvShadowStrength)` scaling the sun term; the car shader lerps from `0.2 + InvShadowStrength` to 1), and only depth textures are bound as shadow samplers (`render.m` sets `shadow_samplers` from the bound texture's format).

**Shadows switched on mid-race (game behaviour, 2026-10-20, `run_shots/shadows_midrace_switch_vs_boot.jpg`):** the Video options' Accept stores the setting and sets LoadedFlagMaybe (00982C39), so the next frame runs the game's full device Reset, which creates the shadow maps; matrices, map size, sampler, cull and fit then match a boot-on run exactly (same-camera 4K check on 15.1.1, x360 fit). What differs: the world's dedicated shadow-caster meshes (scenery named `SHADOW*` with flags 0x300000: hillsides, barriers, poles), which `FUN_006d7c40` merges per scenery section at section load only if `g_ShadowDetail > 0`. Sections loaded before the switch never get them, so barriers and terrain cast no shadow until new sections stream in; the PC game does the same on Windows. A fresh start with shadows saved on is correct. `NFS_TEST_SHADOW_SWITCH=<s>[:<level>|:mark]` (test only) does what Accept does `<s>` seconds into the race (`mark` only marks the frame, for the boot-on comparison); the frame counts as a key press for diag's `key+N`. Scripted path through the menus (verified, but keys get dropped around the Reset at 4K): `ESCAPE`, 4× `RIGHT` (Options), `RETURN`, `RIGHT` (Video), `RETURN`, `2` (Advanced), 5× `DOWN` (Shadow Detail; the greyed FSAA row is skipped), `RIGHT`, `RETURN` (Accept); allow ~6 s per screen at 4K. A fresh `BOOT_USERDATA` runs the first-time detection (shadows 1, `BOOT_REG` ignored): copy a `registry.txt` in.

**Displaced shadows with the X360 fit (port fault, fixed 2026-10-20, branch `shadowoffset`, `run_shots/shadows_x360_fit_receiver_matrix.jpg`):** the user saw wall, fence, building and car shadows far from their casters (two free-roam recordings in Rosewood, moving and slow). `FUN_006e44c0` keeps its fit M1 (playerView x LiSPSM) in a stack local: it copies M1 into view 15's projection for the casters (006E4FEF), then after the casters multiplies the same stack M1 by the texel-centre bias (006E5428) into view 15's projection, which every receiver's `ShadowTransform` reads (World x 00985990+0x40: `FUN_006c8000`, `FUN_006d6aa0`). The X360 light camera only replaced view 15's projection at 006E50C3, so with `NFS_SHADOW_FIT=x360` the casters drew with the X360 fit and the receivers looked the map up through the PC fit (x scale ~30 % apart, depth differing too): 0/492 receivers on 15.1.1 and 0/969 in free roam matched World x casters' view-projection x bias, and a caster's ground footprint came out ~4 m (5 m ahead) to ~10 m (40 m ahead) further along the view direction, ~1 m sideways; the car shadow under the car disappeared. Not speed related: the matrices are built and used in the same frame (the shadow pass `FUN_006e54e0` runs before the player view's draws in the frame's render function), so parked and moving look the same. `x360.m` now also writes the X360 projection into M1 at 006E5428; after: every main-view receiver (world, normal-map, reflect, glossy window, particles, car) matches. `NFS_SHADOW_FIT=pc` was never affected (M1 is its own projection). The earlier "ShadowTransform = World x caster VP x bias" check compared M1 x bias with view 15's projection, which holds by construction; the check that catches this is M1 against view 15's view-projection (both logged as `shadow matrix` in `BOOT_DIAG_DRAWS` frames).

  Front-end platform extension: the active set had none of the six scenes' texture hashes. `tools_snapshot/x360_tex.py` now reads CAREER_SAFEHOUSE, PLATFORMCRIB, CAR_LOT, CUSTOMIZATION_SHOP, CUSTOMIZATION_SHOP_BACKROOM and NEXTGENSKY directly from the ISO by ZDIR path hash; only those LZCs are read, leaving the extract untouched (no memcard, KEY.TXT or unnamed entry). File-level JDLZ is decoded for HD as well as UI, with a 128 MiB file limit (PLATFORMCRIB expands to 34,034,720 bytes; embedded blocks retain the 32 MiB limit). The actual scene sizes extend the older comparison TSV; PC P8 palettes participate in the existing alpha/tone checks. Alpha-capable PC textures retain PC alpha as DXT5 even when opaque, satisfying Init's DXT1 guard. CSHOP_TOOLBOX_NORMAL has no PC scene counterpart and is excluded. The existing Init hook has no world/FE restriction; no renderer change is needed.

  Generate a **new** complete set from this worktree (the existing 386 DDS files, including tone variants, are copied unchanged; the new folder must not already exist):

  ```sh
  "$TOOLS_PY" -I tools_snapshot/x360_tex.py <X360 files> <out dir> --larger <texture comparison table> --mips --pc-alpha <PC game> --tone-match <PC game> --frontend-iso <X360 disc image> --extend-set <HD texture set>
  "$TOOLS_PY" -I tools_snapshot/test_x360_fe_textures.py <X360 disc image> <PC game> <generated HD set> <HD texture set>
  ```

  Select the generated folder with `NFS_X360_TEXTURES="$PWD/recomp/out/hd_textures_mips_alpha_fescenes"`; the default folder is unchanged. Offline audit: 57/57, 54/54, 34/34, 24/24 and 24/24 eligible enlarged replacements in the five textured scenes respectively; NEXTGENSKY 0/0. There are 168 unique new hashes (the shops share their textures, and one of those hashes also occurs in the crib). All pass the runtime's encoded covering-mip RGB ≤12 / alpha ≤16 check, including its integer box rounding and format guard; all six deliberately omitted-scene controls fail. `frontend_scenes.tsv`, `frontend_audit.tsv` and `frontend_memory.tsv` in the generated folder record coverage, per-hash differences and memory. Guest / GPU payload deltas in bytes: safehouse 21,357,908 / 21,357,908; crib 25,592,792 / 14,125,976; car lot 19,647,620 / 19,647,620; each shop 6,578,544 / 6,578,544; sky 0 / 0. One resident copy of every unique new texture adds 73,045,760 guest bytes and 61,578,944 GPU bytes. Metal uses shared memory for these textures, so these are GPU resource payloads rather than separate discrete VRAM. Per-scene guest + GPU payload predicts roughly +12.5–40.7 MiB of RSS; actual RSS/Metal allocatedSize also include alignment, staging and retained validation scratch and need a game run. The initial full-set regeneration exited 132 while scanning existing compressed packs; the incremental path avoids that scan and is the verified command above. Appearance and runtime load cost remain unverified.

- X360 sound mix (`NFS_X360_AUDIO=on|off`, default off, F10 Audio > "X360 sound mix", restart; `runtime/x360audio.c`): the game loads its four mix maps from `Global/InGameMemoryFile.bin` (the same file holds the reverb presets), so with the switch on `CreateFileA` serves that file with the four 9996-byte mix map entries replaced by the X360 extract's, word-swapped (the X360 `GLOBAL/INGAMEMEMORYFILE.BIN`; `NFS_X360_FILES=<dir>` overrides; a missing X360 file keeps the PC's). `BOOT_DIAG` `x360audio:` lines: the maps served, which map `NFSMixMaster::CreateMainMainMap` (004F1EC0) loads and a word of its buffer (+5F8: PC `FF38D8F0`, X360 `0000D8F0`), and every tunnel reverb change (`SFXCTL_Tunnel::SetCurrentReverbType` 004B57E0: type, fade, previous type; types 6/7 appear on entering/leaving a tunnel). Reverb is selected independently with the Reverb option below. `stats.log` `mixrms` and the session `perf.tsv` `rms_*` columns show the per-channel levels. The same switch (A5) also serves the X360's `SOUND/ENGINE/GIN_*.gin` in place of the PC's (`x360audio: GIN_x.gin -> X360 file`; only cars with a Ginsu engine open one) and lays its 35 differing `engineaudio` values over the collections as they load (`x360audio: attrib ...`); and the audioimpact collision volume (A9, 15000 -> 13000, one more `attrib` line); and G3: `SOUND/IG_GLOBAL/TRAFFIC_MB.abk` and `ENV_COMMON_MB.abk` are rebuilt from the PC and X360 files at first use (`runtime/x360abk.c`: X360 S10A/XMA1 sounds decoded to PCM16 with FFmpeg's `xma1`, X360 sample tables converted, PC modules kept; both pairs must match the pinned retail CRCs and decoded PCM) and served from memory, and only then the 21 traffic cars' HornType/TrafficEngType get the X360's values. `BOOT_DIAG` `x360abk:` lines: each bank converted or not (sounds, sample tables, bytes, ms), `G3 on/off`, each bank served; `x360audio: attrib ... pvehicle HornType|TrafficEngType a -> b (G3)`. A10 rides on it too: every other `SOUND/**/*.abk` whose X360 counterpart has the PC's structure (the same slots, sample tables row for row, mono, the same loop flags, not reordered, every sound decoded) is served as the PC file with only its BNKl rebuilt: X360 sound i at 48 kHz PCM16 (codec 8) in PC slot i + 1, all-zero X360 placeholders keeping the PC sample (`x360abk_swap_pc`, read back as the PC parses it). 275 of 301 banks qualify; 26 stay PC (16 sound count: SWTN banks whose PC has an extra placeholder slot, and TRAFFIC/ENV which G3 serves; 5 sample tables differ; 2 stereo FE banks: the PC keeps each channel as its own stream, PT 0x88/0x89, and PCM16 playback of that is unverified; 3 TURBO_TUN_MED reordered). Each bank is converted at its first open (~4 ms for an engine bank, 0.8 s for all) and cached as `~/Library/Caches/NFSMW-port/x360abk/<name>_<PC CRC>_<X360 CRC>_v1.abk` (`NFS_X360ABK_CACHE=<dir>` overrides; 151 MB if every bank is used; temp file + rename; a damaged cache file is converted again; an unwritable cache serves an unlinked temp file), served from the file so nothing stays in memory. `BOOT_DIAG`: one `x360abk: SOUND/... served X360 (converted|cache, sounds, placeholders, bytes, ms)` or `kept PC: <reason>: <detail>` line per bank with running totals (served, kept PC by reason, ms, bytes). Offline proof and the A10 inventory of all 301 X360 banks: `runtime/x360abk_test.c` (build line in its header; `g3`, `allbanks` and `inventory` modes                                                                       ).
- Reverb (A8; `NFS_X360_REVERB=pc|x360`, default **PC**, F10 Audio > Xbox 360 sound > Reverb, order 95, restart): independent of Sound mix, music and the Picture Look preset. With X360 selected, `x360audio.c` reads `GLOBAL/INGAMEMEMORYFILE.BIN` from the usual case-insensitive X360 extract path (`NFS_X360_FILES` overrides), validates the directory and the four FX graphs, and rebuilds the PC memory file with revised offsets and both size fields. Missing files, malformed records/edges or allocation failure keep the PC file. Mix maps still follow Sound mix separately. FX bytes are big-endian on both platforms and are copied without word swapping.
